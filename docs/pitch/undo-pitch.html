What happens to one tool call inside Undo

Every call becomes a row in Postgres. Nothing important lives only in memory.

5Reserve budgetAtomic, so no overspending

Prove

after, and forever

This is the engine in one picture. Check: validate, dedupe, fetch facts from the real system (never trust what the agent claims), apply the YAML rules, reserve budget atomically. Do: write the intent and the idempotency key to Postgres before calling anything, call the provider with that key, record the outcome. "Unknown" is a real state: we never guess. Prove: resolve unknowns, post balanced ledger entries. Code: ProposalService, ExecutionService, RecoveryService.

Where Undo keeps everything

One PostgreSQL database. Every tool call is rows, written before anything goes out.

The work

runs, tasks, actions

One row per tool call: arguments, idempotency key, status, lease, result

The history

action_transitions, attempts

Every status change and every call to the provider. Never edited.

The decisions

policy_versions, approvals

Which rules applied, and who approved which exact arguments

The money

A double-entry ledger. Every entry must add up to zero.

Undo and checks

All state is in one Postgres database, defined in V1__init.sql. The work: runs is one agent session, actions is one row per tool call. The history tables are append-only: a trigger refuses UPDATE and DELETE on action_transitions and postings, so the audit trail cannot be rewritten. The money is a real double-entry ledger with a trigger that rejects any entry not summing to zero. The green strip is the point for a senior engineer: the important rules are enforced by the database itself, not only by Java code. Next slide shows one refund as actual rows.

Fix for problem 1

Exactly once, even when the server dies

₹450 refunded. Once.

Same key, so Payments returned the first result instead of refunding again.

No key at all, like email?Undo never resends on its own. A person checks.
An old worker wakes up late?Its fence number is out of date, so the database rejects its write.
The key line: the idempotency key is created and saved in Postgres before the first call, and every retry reuses it. Walk it: save row and key, call with the key, refund happens, reply lost, worker is kill -9'd. The lease expires, the sweeper marks the action UNKNOWN (we never guess success or failure). The resolver retries with the same key; Payments recognises it and returns the original refund. One refund. Two edge cases: providers without keys go to a human, and a zombie worker is blocked by fencing.

New providers fit the same types: Stripe refunds work like row one, Gmail sends like row three.

This answers "what about email and the rest?". Every tool is one of four types, set by its connector. Refunds have idempotency keys: safest, retry with the same key. Store credit has no key, but we attach a reference, so we look it up before deciding. Email has neither: Undo never resends on its own, it asks a person; this is "at most once", and we say so. Notes and ticket status are setting a value: repeating is harmless. The last column is revert: each type has its own undo, and where there is none, Undo says so. Stripe and Gmail connectors are designed on exactly these types (docs/plans/stripe-gmail-connectors.md).

“Isn’t this just…”

…our activity log?

A log writes down what happened, after it happened. Undo is in the path: it decides before the action, saves the intent before the call, settles every unknown, and can take the action back. A camera records the theft; a bank teller stops it.

…Stripe’s idempotency key?

Stripe checks the key. Someone has to create it, save it before the call, and reuse it after a crash. An agent that asks twice sends two keys. Keys expire after a day. Email has no keys at all.

…what a good backend does?

A backend asks: is this user allowed? Undo also asks: does this action make sense, is it inside this run’s budget, should a person see it, and can we undo the whole run?

These are the questions a senior engineer will ask; answer them before he does. Log: passive versus in the path. Idempotency: Undo and the provider are two layers. Undo catches the agent asking twice and makes one action with one saved key; the provider catches Undo's retries. Good backend: it makes each request safe; Undo makes the agent safe. Be honest: the better the backend, the less Undo adds on crashes, but the agent control part still applies.

What it does not promise

Email is at most once

No keys and no reliable lookup. If a send times out, Undo never resends; a person checks.

Some things can’t be undone

A paid-out refund or a sent email. Undo says so and drafts a correction for approval.

It rests on one stated assumption

A request the provider hasn’t answered in about 70 seconds never lands later. Break that in the simulator and 4.8% of runs fail, so we say it out loud.

It contains prompt injection, it doesn’t detect it

A tricked agent still can’t get past the rules or the budget.

One open finding

A one-million-run test found 22 runs where a revert report misses money that came back later. A design fix is pending.

One real connector so far

It talks to a mock store today. Stripe and Gmail connectors are designed, not built.

Saying the limits builds more trust than hiding them. The 70-second assumption is called A1; with it broken, 4,799 of 100,000 simulated runs fail, which shows the guarantees depend on it. The 22 runs are all one invariant, INV-6, about revert report accounting, not about duplicate money. It is a design decision for the next milestone.
